# [EPIC-06] Рахунки й платежі

## 1. Загальний опис

Садок виставляє дитині рахунки за місяць, батьки їх оплачують, а система зберігає, хто скільки винен і скільки грошей надійшло (FR-014, NFR-11, розділ 2.6 вимог «оплачувати заняття та харчування», мета 1.2 «вести облік платежів»). Замінює відкладений TS-04.5.

- **Рахунок (invoice)** — нарахування: скільки винні за період і за що. Рядки й суми фіксуються в момент виставлення, тож зміна цін не змінює вже виставлені рахунки.
- **Платіж (payment)** — гроші, що фактично надійшли: сума, дата, спосіб. Один платіж закриває один або кілька неоплачених рахунків однієї дитини, і лише повністю.

Справжньої платіжної системи немає: «оплатити» означає записати платіж. Батьки «платять карткою», менеджер записує готівку.

## 2. Межі епіка (Scope)

### In-Scope

- Виставлення рахунків одній дитині та всім дітям садка за місяць.
- Річний рахунок за навчання для дітей на річному плані (FR-013) і щомісячні рахунки за харчування (BR-32).
- Платежі з захистом від повторного запиту (`Idempotency-Key`, NFR-11).
- Перегляд рахунків і історії платежів за ролями: батьки бачать лише своїх дітей (NFR-04).
- Покриття тестами: суми рядків, правила виставлення й оплати, доступ.

### Out-of-Scope

- Справжня оплата через платіжну систему.
- Часткова оплата рахунку й повернення коштів.
- Платіж за кількох дітей однієї сім'ї: платіж прив'язаний до однієї дитини (FR-014).
- Пеня за прострочення й нагадування.
- Фактичні витрати (Expense): витрати садка лишаються розрахунковими, як в EPIC-04.

## 3. Декомпозиція задач (Breakdown)

### 🛠 Technical Stories

- [x] **TS-06.1: Рахунки**
    - **Колекція `invoices`:**

        | Поле          | Тип                  | Що означає                                                          |
        | ------------- | -------------------- | ------------------------------------------------------------------- |
        | `kidId`       | посилання, `setNull` | дитина; після видалення дитини (FR-018) рахунок лишається в історії |
        | `kidName`     | рядок                | ім'я й прізвище дитини на момент виставлення                        |
        | `groupId`     | посилання, `setNull` | група дитини на момент виставлення                                  |
        | `kind`        | `MONTHLY` / `ANNUAL` | рахунок за місяць або за навчання на рік уперед                     |
        | `periodStart` | `date`               | перший день періоду: `2026-11-01`                                   |
        | `periodEnd`   | `date`               | останній день: `2026-11-30` для місяця, `2027-10-31` для року       |
        | `lines`       | масив                | рядки рахунку, зафіксовані при виставленні                          |
        | `total`       | число                | сума рядків                                                         |
        | `status`      | `UNPAID` / `PAID`    | чи оплачено                                                         |

    - **Рядки** (`lines`), приклад для дитини 3 років із пільгою 10%:
        - щомісячний план: `TUITION 15000`, `DISCOUNT −1500`, `MEALS 400 × 22 = 8800`, разом 22 300;
        - річний план, рахунок `ANNUAL`: `TUITION 15000 × 12 = 180000`, `DISCOUNT −18000`, `ANNUAL_DISCOUNT −19440`, разом 142 560 = 11 880 × 12; щомісячні рахунки — лише `MEALS`.

    - **Ендпоінти:**

        | Метод й шлях                | Хто                    | Що робить                                                                   |
        | --------------------------- | ---------------------- | --------------------------------------------------------------------------- |
        | `POST /api/invoices`        | ADMIN, MANAGER         | `{ kidId, period: "2026-11" }`: виставляє дитині все, що належить за місяць |
        | `POST /api/invoices/batch`  | ADMIN, MANAGER         | `{ period }`: те саме для кожної дитини в групі; вже виставлене пропускає   |
        | `GET /api/invoices`, `/:id` | ADMIN, MANAGER, PARENT | список з `where` і `sort`; батьки бачать лише рахунки своїх дітей           |
        | `DELETE /api/invoices/:id`  | ADMIN, MANAGER         | видаляє неоплачений рахунок, наприклад виставлений помилково                |

    - **Acceptance Criteria:**
        - За місяць дитині виставляється рахунок `MONTHLY`: харчування, а навчання — якщо його не покриває річний рахунок.
        - Дитині на річному плані, чий місяць ще не покритий річним рахунком, виставляється й рахунок `ANNUAL` на 12 місяців від цього.
        - Повторне виставлення за той самий місяць дає `409 INVOICE_EXISTS`; batch таких дітей пропускає.
        - Дитині без групи рахунок не виставляється: `422 KID_NOT_ENROLLED` (дитина без групи не відвідує садок).
        - Зміна цін і пільг не змінює вже виставлені рахунки.
        - Оплачений рахунок не видаляється: `409 INVOICE_PAID`.
        - Батьки бачать лише рахунки своїх дітей; чужий рахунок — `403`.

- [x] **TS-06.2: Платежі та ідемпотентність (FR-014, NFR-11)**
    - **Колекція `payments`:** дитина (`setNull`) і її ім'я, сума, спосіб (`CARD` / `CASH`), коли сплачено, хто записав (обліковий запис), `operationId` — значення заголовка `Idempotency-Key`, унікальне. Рахунки платежу — ті, у яких `paymentId` вказує на нього: рахунок отримує поля `paymentId` (посилання на `payments`) і `paidAt` (коли оплачено).
    - **Ендпоінти:** `POST /api/payments` `{ invoiceIds, method }` (ADMIN, MANAGER, PARENT); `GET /api/payments`, `/:id` — з рахунками платежу.
    - **Acceptance Criteria:**
        - Суму рахує сервер: сума рахунків платежу.
        - Платіж покриває лише неоплачені рахунки однієї дитини: інакше `409 INVOICE_PAID` або `422 INVOICES_OF_DIFFERENT_KIDS`.
        - Батьки платять лише за своїх дітей: інакше `403`.
        - Платіж і позначення рахунків оплаченими — одна транзакція: при помилці база не змінюється (NFR-10).
        - Повторний запит з тим самим `Idempotency-Key` і тими самими рахунками повертає вже створений платіж (`200`), а не створює другий; той самий ключ з іншими рахунками — `422 IDEMPOTENCY_KEY_REUSED`.
        - Заголовок `Idempotency-Key` необов'язковий; довший за 100 символів — `400 INVALID_IDEMPOTENCY_KEY`.
        - Платежі не видаляються: це історія руху грошей.

- [x] **TS-06.3: Звіт за отриманими платежами (FR-017)**
    - **Опис:** `GET /api/finance/report?basis=CASH&month=2026-11`: доходи від платежів, що надійшли за місяць, окремо навчання й харчування, по групах. Витрати — розрахункові, як у звіті за нарахуваннями, і це явно сказано у відповіді.
    - **Acceptance Criteria:**
        - Річна передоплата потрапляє цілком у місяць оплати; у звіті за нарахуваннями — по 1/12 на місяць (FR-017).
        - Звіт за нарахуваннями лишається звітом за замовчуванням.
        - Місяць — за київським часом: відповідь містить його межі (`from`, `to`).
        - Дохід від рахунків групи, видаленої відтоді, показано окремо (`withoutGroup`).
        - `month` без `basis=CASH`, `basis=CASH` без `month` — `400 INVALID_QUERY`.

- [x] **TS-06.4: Postman, seed, документація**
    - Тека в «Kindergarten tour»: виставити рахунки за місяць → батьки бачать свій рахунок → оплачують → повторний запит з тим самим ключем не створює другого платежу → чужий рахунок дає `403`.
    - Seed виставляє рахунки за поточний місяць і частину з них оплачує.
    - README і services.md.

## 4. Перелік User Stories / Задач

- [x] **US-06.1: Рахунки**
    - **Як** менеджер, **я хочу** виставити рахунки всім дітям за місяць одним запитом, **щоб** не рахувати суми вручну.
- [x] **US-06.2: Оплата**
    - **Як** батьки, **я хочу** бачити рахунки своєї дитини й оплачувати їх, **щоб** знати, скільки я винен, і не платити двічі.
- [x] **US-06.3: Історія платежів**
    - **Як** дід, **я хочу** бачити, хто й коли заплатив і хто винен, **щоб** контролювати надходження.
