# [EPIC-02] Розширення REST API та цілісність даних

## 1. Загальний опис

Надбудувати над CRUD з EPIC-01 зручний REST-інтерфейс для зв'язків між сутностями, діагностику цілісності даних і пакетне додавання дітей у групу, а також доробити бізнес-правила наявних сутностей. Нових сутностей епік не додає: усе працює над тими, що вже є.

Принцип, на якому побудовані правила епіка: **під час запису правило перевіряється з боку того, хто приєднується** (дитина до групи, батько до дитини). Те, що стало неправильним пізніше через зміну деінде (групі змінили вік, група втратила вихователя), запис не блокує, а знаходить діагностика.

## 2. Межі епіка (Scope)

### In-Scope

- Вкладені шляхи для читання зв'язків (`/api/groups/:id/kids` тощо).
- Діагностичні ендпоінти `/api/consistency` (FR-019).
- Пакетне додавання дітей у групу (FR-020).
- Похідна ознака «група відвідує логопеда» (FR-021).
- Сортування за порядком внесення й за алфавітом (FR-023).
- Заборона змінювати стать батьків, які вже вказані в дітей (BR-12).
- Покриття тестами: сервіси, HTTP, кожне правило.

### Out-of-Scope

- Автентифікація та авторизація - буде в EPIC-03.
- Пакетне створення сутностей і пакетне видалення дітей з групи.
- Заборона при записі для BR-02 з боку групи (зміна віку групи), BR-08 з боку групи (група втрачає кімнату, вихователя чи помічника) і BR-11 (дитина без двох батьків): ці випадки знаходить діагностика.
- Реалізація розкладу
- Реалізація підтримки фінансових операцій

## 3. Декомпозиція задач (Breakdown)

### 🛠 Technical Stories

- [ ] **TS-02.1: Вкладені шляхи для зв'язків**
    - **Опис:** Додати ендпоінти, що читають записи, пов'язані з іншим записом. Лише читання: записи змінюються через свої канонічні адреси (`/api/kids/:id` тощо). Виняток — нотатки, які існують лише з дитиною й уже мають повний CRUD під `/api/kids/:kidId/notes`.

    - **Ендпоінти:**
        - `GET /api/groups/:id/kids` — діти групи;
        - `GET /api/parents/:id/kids` — діти батька чи матері, в будь-якій ролі;
        - `GET /api/groups/:id/room` — кімната групи;
        - `GET /api/educators/:id/group`, `GET /api/assistants/:id/group` — група працівника;
        - `GET /api/subjects/:id/teachers`, `GET /api/subjects/:id/rooms` — хто викладає предмет і де;
        - `GET /api/discounts/:id/kids` — діти з пільгою.

    - **Acceptance Criteria:**
        - Списки підтримують ті самі `where`, `sort`, `limit` та `offset`, що й звичайні списки, і повертають сторінку того самого формату.
        - Неіснуючий батьківський запис дає `404 NOT_FOUND`.
        - Порожній зв'язок дає порожню сторінку (для списків) або `null` (для одного запису).
        - Неправильний `id` у шляху дає `400 INVALID_ID` до звернення до сервісу.

- [ ] **TS-02.2: Діагностика цілісності (FR-019)**
    - **Опис:** Дати адміну й менеджеру спосіб знайти проблемні записи без складних фільтрів. Кожна проблема має машинний код, як і помилки API.

    - **Ендпоінти:**
        - `GET /api/consistency` — зведення: для кожної проблеми її код, сутність, кількість записів і посилання на них. Самих записів зведення не містить, тож його розмір не залежить від розміру бази.
        - `GET /api/consistency/{kids|groups|educators|assistants}` — проблемні записи цієї сутності, у кожного список його проблем. Підтримує `?problem=<код>`, `limit` та `offset`.

    - **Проблеми:**

        | Сутність   | Код                         | Звідки                       |
        | ---------- | --------------------------- | ---------------------------- |
        | kids       | `KID_WITHOUT_GROUP`         | FR-019                       |
        | kids       | `KID_INCOMPLETE_PARENTS`    | BR-11                        |
        | kids       | `KID_GROUP_AGE_MISMATCH`    | BR-02 після зміни віку групи |
        | groups     | `GROUP_WITHOUT_EDUCATOR`    | FR-019                       |
        | groups     | `GROUP_WITHOUT_ASSISTANT`   | FR-019                       |
        | groups     | `GROUP_WITHOUT_ROOM`        | FR-019                       |
        | groups     | `GROUP_NOT_READY_WITH_KIDS` | BR-08 з боку групи           |
        | educators  | `EDUCATOR_WITHOUT_GROUP`    | FR-019                       |
        | assistants | `ASSISTANT_WITHOUT_GROUP`   | FR-019                       |

    - **Acceptance Criteria:**
        - Зведення перелічує лише проблеми, що мають хоча б один запис.
        - Запис із кількома проблемами з'являється в списку один раз, з усіма своїми кодами.
        - Невідомий код у `?problem=` або невідома сутність у шляху дає `400`.
        - Діагностика лише читає дані й нічого не змінює.

- [ ] **TS-02.3: Пакетне додавання дітей у групу (FR-020)**
    - **Опис:** `POST /api/groups/:id/kids` з тілом `{ "kidIds": [...] }` переводить кількох дітей у групу одним запитом.

    - **Acceptance Criteria:**
        - Усі діти додаються в одній транзакції: або всі, або жоден.
        - BR-02 (вік дитини збігається з віком групи) і BR-08 (у групи є кімната, вихователь і помічник) перевіряються для кожної дитини.
        - BR-03 (не більше 20 дітей) перевіряється для групи разом з усіма новими дітьми.
        - Помилка перелічує в `details` усіх дітей, які не підходять, а не лише першу.
        - Дитина, що вже в цій групі, не рахується двічі; повтор `id` у тілі або неіснуюча дитина дає `422`.

## 4. Перелік User Stories / Задач

- [ ] **US-02.1: Пов'язані записи**
    - **Як** адміністратор, **я хочу** отримувати дітей групи, дітей батьків, групу працівника тощо окремим запитом, **щоб** не складати фільтри вручну.
- [ ] **US-02.2: Пошук проблемних записів (FR-019)**
    - **Як** адміністратор або менеджер, **я хочу** бачити, які записи порушують правила садка й чому, **щоб** швидко їх виправити.
- [ ] **US-02.3: Пакетне додавання в групу (FR-020)**
    - **Як** адміністратор, **я хочу** додати кількох дітей у групу одним запитом, **щоб** не робити це для кожної дитини окремо.
- [ ] **US-02.4: Групи, що відвідують логопеда (FR-021)**
    - **Як** адміністратор, **я хочу** бачити в групі ознаку `attendsSpeechLessons` і фільтрувати за нею групи, **щоб** знати, яким групам потрібні заняття з логопедом.
    - **Acceptance Criteria:** ознака дорівнює `true`, якщо в групі є хоча б одна дитина з `needsSpeechLessons`; у базі вона не зберігається, а обчислюється при читанні.
- [ ] **US-02.5: Сортування (FR-023)**
    - **Як** користувач, **я хочу** отримувати списки за порядком внесення або за алфавітом, **щоб** швидше знаходити потрібний запис.
    - **Acceptance Criteria:**
        - `?sort=id` повертає записи в порядку внесення (UUIDv7 починається з часу створення); `?sort=lastName,firstName` — за алфавітом.
        - Алфавітний порядок не залежить від регістру: `adams` стоїть перед `Baker`, а не після всіх великих літер, як при порівнянні кодів символів. Основні дані англійською, але порядок правильний і для української: і, ї, є, ґ та апостроф стоять на своїх місцях.
        - Порядок за замовчуванням задокументований.
- [ ] **US-02.6: Стать батьків (BR-12)**
    - **Як** адміністратор, **я хочу**, щоб система не давала змінити стать матері чи батька, які вже вказані в дитини, **щоб** у дитини завжди були мати й батько.
    - **Acceptance Criteria:** PATCH та PUT `/api/parents/:id` зі зміною `sex` для батька, вказаного хоча б в одної дитини як `motherId` чи `fatherId`, дає `409`; зміна інших полів працює як раніше.

## 5. Критерії готовності (Definition of Done)

- [ ] Для кожного зв'язку з TS-02.1 є ендпоінт, що повертає пов'язані записи.
- [ ] Адмін може знайти всі проблеми з TS-02.2 без жодного фільтра.
- [ ] Пакетне додавання дітей у групу дотримується тих самих правил, що й додавання однієї дитини.
- [ ] Реалізовані FR-021, FR-023 та BR-12 з боку батьків.
- [ ] Кожне правило й кожен ендпоінт покриті тестами; `npm test` і `npm run lint` проходять.
