# File database and REST API

The server uses the native Node.js file system. It does not connect to SQL or
NoSQL software. Each directory directly under `database/` is a collection,
each collection has a tracked `config.json`, and each record is stored in its
own `<uuid>.json` file. Runtime record files are ignored by Git.

The checked-in collections are `kids`, `groups`, `parents`, `teachers`, and
`rooms`. Add a collection by adding a directory and a `config.json` file before
starting the server. The config declares `table`, the `id` primary key, column
types and constraints, optional defaults, and fields to index in memory.

## HTTP endpoints

All records are served beneath `/api`:

| Method   | Path                   | Result                                                                        |
| -------- | ---------------------- | ----------------------------------------------------------------------------- |
| `GET`    | `/api`                 | List configured collections.                                                  |
| `GET`    | `/api/:collection`     | List records. Supports `limit`, `offset`, and a JSON `where` query parameter. |
| `POST`   | `/api/:collection`     | Create a record and return its generated UUID.                                |
| `GET`    | `/api/:collection/:id` | Read one record by UUID.                                                      |
| `PUT`    | `/api/:collection/:id` | Replace a record. All required fields must be supplied.                       |
| `PATCH`  | `/api/:collection/:id` | Update selected fields.                                                       |
| `DELETE` | `/api/:collection/:id` | Delete one record.                                                            |

Example filtered request:

```text
GET /api/kids?where=%7B%22age%22%3A3%7D&limit=20&offset=0
```

Responses use JSON. Creates return `201` and a `Location` header; deletes
return `204`; invalid input returns `4xx` JSON with an error code. New record
IDs are UUIDv7 values generated by the server. Their timestamp prefix makes
sorting by ID chronological to millisecond precision; IDs created in the same
millisecond may appear in either order. Existing UUIDv4 record IDs remain valid,
but do not contain a creation timestamp.

## Storage guarantees and boundaries

Updates to one record are queued in process and written to a temporary file
before an atomic rename. In-memory indexes are rebuilt from record files when
the server starts and are kept in sync after successful creates, updates, and
deletes. Reads by ID use the UUID file directly. This locking protects requests
handled by one server process; it is not a cross-process lock or a distributed
transaction system.

The first CRUD increment does not yet enforce links between collections or
cascade deletes. For example, deleting a group does not delete or reassign its
children. Define and implement those business rules separately before relying
on linked records in production.

Set `DATABASE_DIR` to use a different local directory. The server listens on
`0.0.0.0` and the port from `PORT` (default `3000`), so it can run in a
container or a hosting environment that supplies a port. Use persistent disk
storage for the selected database directory; ephemeral hosting filesystems can
lose records when an instance is replaced.
