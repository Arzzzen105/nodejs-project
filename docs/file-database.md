# Файлова база даних

Власний рушій бази даних на файлах, без зовнішніх СУБД і без готових файлових баз. Код — у `src/storage`, публічний вхід — `src/storage/file-database.js`.

```js
import { FileDatabase, eq, and, gte } from './storage/file-database.js';

const db = new FileDatabase(); // директорія з DATABASE_DIR або ./database
await db.init();

const kid = await db.create('kids', {
    firstName: 'Оля',
    lastName: 'Бойко',
    age: 3,
});
const page = await db.list('kids', {
    where: { age: 3 },
    sort: 'lastName',
    limit: 20,
});
await db.transaction(async (tx) => {
    /* кілька змін атомарно */
});
await db.close();
```

## 1. Модель зберігання

- **Колекція = директорія, запис = JSON-файл.**

    ```
    database/
    ├── kids/
    │   ├── config.json                              ← схема (у Git)
    │   ├── 0190f3a2-7c1e-7b4d-9a3f-5e2d8c1b0a99.json ← запис (не в Git)
    │   └── ...
    └── groups/
        ├── config.json
        └── ...
    ```

- **Первинний ключ** — `id`, UUID **v7**. Його завжди генерує рушій: передати `id` при створенні чи змінити його не можна. UUIDv7 починається з мітки часу, тож порядок за `id` — це порядок створення.
- **У пам'яті** тримаються лише `id` записів та індекси. Самі записи читаються з диска, коли потрібні.
- **Кожен файл пишеться атомарно:** спершу у тимчасовий файл, потім `fsync` і `rename` на місце. Записаний наполовину файл неможливий.
- **Директорію бази** задає змінна `DATABASE_DIR` (за замовчуванням `./database`). На хостингу вона має бути на постійному диску.

## 2. Схема колекції (`config.json`)

Колекція з'являється, коли в директорії бази є піддиректорія з `config.json`. Ім'я колекції — це ім'я директорії: малі латинські літери, цифри, `-` і `_`, на початку — літера.

```json
{
    "table": "kids",
    "primaryKey": "id",
    "columns": {
        "firstName": {
            "type": "string",
            "required": true,
            "minLength": 1,
            "maxLength": 100
        },
        "lastName": {
            "type": "string",
            "required": true,
            "minLength": 1,
            "maxLength": 100
        },
        "age": { "type": "integer", "required": true, "min": 2, "max": 5 }
    },
    "indexes": ["lastName"]
}
```

| Ключ         | Обов'язковий     | Значення                                         |
| ------------ | ---------------- | ------------------------------------------------ |
| `table`      | так              | збігається з іменем директорії                   |
| `primaryKey` | так              | завжди `"id"`; колонку `id` оголошувати не можна |
| `columns`    | так              | колонки та їхні правила                          |
| `indexes`    | так (можна `[]`) | колонки, які треба індексувати (розділ 5)        |

### Типи колонок

`string`, `number` (скінченне число), `integer` (ціле), `boolean`, `object` (простий JSON-об'єкт), `array`.

### Опції колонки

| Опція                    | Для типів                                | Значення                                                    |
| ------------------------ | ---------------------------------------- | ----------------------------------------------------------- |
| `required`               | усі                                      | поле обов'язкове                                            |
| `nullable`               | усі                                      | дозволено `null`                                            |
| `default`                | усі                                      | значення, якщо поле не передали при створенні (і при `PUT`) |
| `min`, `max`             | `number`, `integer`                      | межі включно                                                |
| `minLength`, `maxLength` | `string`                                 | довжина включно                                             |
| `enum`                   | усі скалярні                             | список дозволених значень                                   |
| `pattern`                | `string`                                 | регулярний вираз                                            |
| `unique`                 | `string`, `number`, `integer`, `boolean` | значення не повторюється (розділ 7)                         |
| `references`             | `string`                                 | посилання на запис іншої колекції (розділ 6)                |
| `items.references`       | `array`                                  | масив посилань (розділ 6)                                   |

### Приклади

Рядок із форматом та значенням за замовчуванням:

```json
"phone": { "type": "string", "nullable": true, "default": null, "pattern": "^\\+380\\d{9}$" }
```

Перелік значень:

```json
"role": { "type": "string", "required": true, "enum": ["teacher", "assistant", "manager"] }
```

Число з межами та значенням за замовчуванням:

```json
"capacity": { "type": "integer", "required": true, "default": 20, "min": 1, "max": 20 }
```

Унікальний email, який можна не вказувати:

```json
"email": { "type": "string", "nullable": true, "default": null, "maxLength": 254, "unique": true }
```

Посилання на групу (дитина може бути без групи):

```json
"groupId": {
    "type": "string",
    "nullable": true,
    "default": null,
    "references": { "collection": "groups", "onDelete": "setNull" }
}
```

Масив посилань:

```json
"childIds": {
    "type": "array",
    "default": [],
    "items": { "references": { "collection": "kids", "onDelete": "remove" } }
}
```

Довільний об'єкт (наприклад, налаштування):

```json
"settings": { "type": "object", "default": {} }
```

### Перевірка конфігу

Конфіг перевіряється при старті. Помилка в ньому зупиняє запуск з `INVALID_CONFIG`, і повідомлення вказує колекцію та колонку. Перевіряється, зокрема:

- невідомі ключі на будь-якому рівні: одрук на кшталт `"requred"` — помилка, а не тихе ігнорування;
- типи опцій: `required`/`nullable`/`unique` — булеві значення; `min`/`max` — скінченні числа; `minLength`/`maxLength` — невід'ємні цілі;
- узгодженість: `min ≤ max`, `minLength ≤ maxLength`, опції підходять до типу колонки (`min` на рядку — помилка);
- `enum`: непорожній масив значень потрібного типу;
- `default` проходить усі правила своєї колонки;
- `pattern` — коректний регулярний вираз;
- `references`: колекція існує, правило `onDelete` дозволене для цього типу колонки;
- `indexes` — лише існуючі скалярні колонки.

### Як застосовується схема до записів

- **`create`:** невідомі поля дають помилку; відсутні поля отримують `default`; `required` без значення дає помилку; кожне поле перевіряється за правилами колонки.
- **`update` (PATCH):** переданий об'єкт зливається з поточним записом, а результат перевіряється повністю.
- **`update` з `replace: true` (PUT):** запис замінюється цілком, як при створенні, зокрема із застосуванням `default`.
- **Записи, що не відповідають схемі** (наприклад, створені до зміни конфігу), завантажуються, але дають попередження (розділ 10). `PATCH` такого запису відкидає поля, яких уже немає в схемі, а відсутню нову `required`-колонку вимагає передати. Так старі записи виправляються поступово, без міграцій.

## 3. Операції та HTTP API

### Методи `FileDatabase`

| Метод                                     | Повертає                                   | Опис                                                                                                    |
| ----------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `new FileDatabase(root?, options?)`       |                                            | `root` — директорія бази; `options.logger`, `options.transactionTimeout` (мс, за замовчуванням `10000`) |
| `init()`                                  | `Promise<this>`                            | відкриває базу (розділ 10)                                                                              |
| `close()`                                 | `Promise<void>`                            | коректно закриває базу (розділ 10)                                                                      |
| `collections()`                           | `string[]`                                 | імена колекцій                                                                                          |
| `schema(name)`                            | `object`                                   | копія `config.json` колекції                                                                            |
| `create(name, input)`                     | `Promise<record>`                          | створює запис                                                                                           |
| `get(name, id)`                           | `Promise<record>`                          | запис за `id`                                                                                           |
| `list(name, options?)`                    | `Promise<{ items, total, limit, offset }>` | пошук (розділ 4)                                                                                        |
| `update(name, id, changes, { replace? })` | `Promise<record>`                          | `PATCH`, або `PUT` при `replace: true`                                                                  |
| `delete(name, id)`                        | `Promise<{ deleted, updated }>`            | видаляє запис і застосовує правила зв'язків                                                             |
| `transaction(fn, { timeout? })`           | `Promise<результат fn>`                    | атомарна група змін (розділ 8)                                                                          |
| `warnings`                                | `object[]`                                 | попередження останнього `init`                                                                          |

Кожен `create`, `update` і `delete` — це окрема атомарна транзакція з однієї операції. Повернені записи — копії: їхня зміна не впливає на базу.

```js
const kid = await db.create('kids', {
    firstName: 'Оля',
    lastName: 'Бойко',
    age: 3,
});
// → { id: '0190f3a2-…', firstName: 'Оля', lastName: 'Бойко', age: 3, groupId: null }

await db.get('kids', kid.id);
await db.update('kids', kid.id, { age: 4 }); // PATCH
await db.update(
    'kids',
    kid.id,
    { firstName: 'Оля', lastName: 'Бойко', age: 4 },
    { replace: true }
); // PUT

const report = await db.delete('groups', groupId);
// → { deleted: [{ collection: 'groups', id: groupId }],
//     updated: [{ collection: 'kids', id: '…', fields: ['groupId'] }, …] }   // хто втратив посилання
```

### HTTP API

Ресурси доступні під `/api`:

| Метод    | Шлях                   | Результат                                        |
| -------- | ---------------------- | ------------------------------------------------ |
| `GET`    | `/api`                 | `{ collections: [...] }`                         |
| `GET`    | `/api/:collection`     | пошук: `where` (JSON), `sort`, `limit`, `offset` |
| `POST`   | `/api/:collection`     | `201`, запис і заголовок `Location`              |
| `GET`    | `/api/:collection/:id` | запис                                            |
| `PUT`    | `/api/:collection/:id` | повна заміна запису                              |
| `PATCH`  | `/api/:collection/:id` | зміна окремих полів                              |
| `DELETE` | `/api/:collection/:id` | `204` без тіла                                   |

Помилки повертаються у форматі `{ "error": { "code": "...", "message": "..." } }` зі статусом із розділу 12. Для статусів `5xx` текст замінюється загальним, а подробиці пишуться в лог.

## 4. Запити: фільтри, сортування, пагінація

```js
db.list(name, {
    where, // фільтр JSON-об'єктом — зручно для HTTP
    predicate, // або фільтр предикатами в коді (якщо задано, where ігнорується)
    sort, // 'lastName', '-age', 'lastName,-age' або ['lastName', '-age']
    limit, // 1–500, за замовчуванням 100
    offset, // ≥ 0, за замовчуванням 0
});
// → { items: [...], total: <усього знайдено>, limit, offset }
```

Фільтр можна задати двома рівноцінними способами:

- **`where`** — JSON-об'єкт. Підходить для HTTP-запитів і простих умов. Значення перевіряються за схемою колекції.
- **`predicate`** — функції `eq`, `and`, `or`… з `file-database.js`. Підходить для коду сервісів і складних умов. Вкладення довільне, є `custom`.

### Умови: однакові запити у двох стилях

Імпорт для прикладів з предикатами:

```js
import {
    eq,
    ne,
    gt,
    gte,
    lt,
    lte,
    range,
    inList,
    and,
    or,
    custom,
    all,
} from './storage/file-database.js';
```

**Рівність**

```js
db.list('kids', { where: { age: 3 } });
db.list('kids', { where: { age: { eq: 3 } } }); // те саме
db.list('kids', { predicate: eq('age', 3) });
```

```text
GET /api/kids?where={"age":3}
```

**Без значення (`null`)** — наприклад, діти без групи:

```js
db.list('kids', { where: { groupId: null } });
db.list('kids', { predicate: eq('groupId', null) });
```

**Нерівність** (записи без цього поля теж підходять):

```js
db.list('teachers', { where: { role: { ne: 'manager' } } });
db.list('teachers', { predicate: ne('role', 'manager') });
```

**Діапазон**

```js
db.list('kids', { where: { age: { gte: 3, lt: 5 } } });
db.list('kids', { predicate: range('age', { gte: 3, lt: 5 }) });
db.list('kids', { predicate: and(gte('age', 3), lt('age', 5)) }); // те саме
```

```text
GET /api/kids?where={"age":{"gte":3,"lt":5}}
```

**Одне з кількох значень (`IN`)**

```js
db.list('teachers', { where: { role: { in: ['teacher', 'assistant'] } } });
db.list('teachers', { predicate: inList('role', ['teacher', 'assistant']) });
```

**Кілька умов одночасно (`AND`)** — у `where` це просто кілька полів:

```js
db.list('kids', { where: { groupId, age: { gte: 4 } } });
db.list('kids', { predicate: and(eq('groupId', groupId), gte('age', 4)) });
```

**Записи за `id`** — для `id` дозволені лише пряме значення, `eq` та `in`:

```js
db.list('kids', { where: { id: { in: [idA, idB] } } });
db.list('kids', { predicate: inList('id', [idA, idB]) });
```

**Лише програмно: `OR`, вкладені умови, довільна перевірка**

```js
// діти групи, яким менше 3 років або які відвідують логопеда
db.list('kids', {
    predicate: and(
        eq('groupId', groupId),
        or(lt('age', 3), eq('needsSpeechTherapy', true))
    ),
});

// довільна синхронна перевірка запису
db.list('kids', { predicate: custom((kid) => kid.firstName.startsWith('О')) });

// усі записи
db.list('kids', { predicate: all() });
```

`custom` завжди читає записи з диска, тож для умов, які можна виразити іншими предикатами, краще використовувати їх. Асинхронна функція в `custom` дає помилку.

### Правила `where`

- **Значення поля без операторів** означає рівність. Оператори: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`.
- **Невідоме поле, невідомий оператор чи порожній `{}`** дають `400 INVALID_QUERY`: помилка у фільтрі ніколи не перетворюється на «повернути все».
- **`in`** має бути масивом.
- **Діапазони** дозволені лише для `string`, `number` та `integer`. Межа не може бути `null`. Рядки порівнюються як рядки, числа — як числа. `null`, відсутні значення та значення іншого типу в діапазон не потрапляють.
- **Перевірка значень за схемою:**
    - `eq` та `in` перевіряються повністю (тип, `min`/`max`, `enum`, `pattern`): шукати значення, яке не може існувати, — помилка;
    - межі діапазонів і `ne` перевіряються лише за типом: `{ age: { lt: 10 } }` дозволено навіть при `max: 5`, а для `integer` дозволено й дробову межу (`{ age: { gt: 2.5 } }`).
- **Колонки типу `object`:** об'єкт без операторів означає рівність усього об'єкта (`{ settings: { theme: 'dark' } }`); оператори не можна змішувати зі звичайними ключами.

### Правила предикатів

Предикати приймають лише значення, які можуть зберігатися в JSON-записі: рядки, скінченні числа, `true`/`false`, `null`, прості об'єкти й масиви. `undefined`, `NaN`, `BigInt`, `Date` тощо одразу дають `TypeError`. Межі діапазонів — числа (дозволено `±Infinity`) або рядки. `-0` вважається рівним `0`. Завдяки цьому результат фільтра не залежить від того, чи є на полі індекс.

### Сортування

```js
db.list('kids', { sort: 'lastName' }); // за зростанням
db.list('kids', { sort: '-age' }); // «-» = за спаданням
db.list('kids', { sort: 'lastName,firstName' }); // кілька ключів
db.list('kids', { sort: ['groupId', '-age'] }); // те саме масивом
```

```text
GET /api/kids?sort=lastName,-age
GET /api/kids?sort=lastName&sort=-age
```

- **Сортувати можна** за `id` і за колонками `string`, `number`, `integer` та `boolean`. Інші поля дають `400 INVALID_QUERY`.
- **Рядки** — за українською абеткою («Ґ» одразу після «Г»), цифри всередині рядка порівнюються як числа («Група 2» перед «Група 10»).
- **`null` і відсутні значення** завжди в кінці, в обох напрямках.
- **Однакові значення** впорядковуються за `id`, тобто за часом створення, тож пагінація стабільна.
- **Без `sort`** записи йдуть у порядку створення.

### Пагінація

```js
const page = await db.list('kids', { sort: 'lastName', limit: 20, offset: 40 });
// page.items — записи 41–60, page.total — скільки всього підходить під фільтр
```

```text
GET /api/kids?sort=lastName&limit=20&offset=40
```

## 5. Індекси

Індекс — це мапа «значення поля → id записів» у пам'яті. Умова на індексованому полі виконується без читання файлів. Без індексу рушій читає записи-кандидати з диска; на сотнях записів це непомітно.

- **Вручну:** поля в `indexes` конфігу. Варто індексувати поля, за якими часто фільтрують.
- **Автоматично:** усі колонки з `references` і `unique`.
- **Масиви посилань** (`items.references`) індексуються по елементах. Цей індекс внутрішній: він пришвидшує пошук посилань при видаленні, а на фільтри не впливає.
- **Індекси перебудовуються** при кожному старті з файлів записів і оновлюються при кожному комміті.

Результат запиту не залежить від того, чи є індекс: він впливає лише на швидкість.

## 6. Зв'язки між колекціями

Колонка може посилатися на запис іншої (або своєї ж) колекції. Рушій гарантує, що посилання ніколи не вказує на запис, якого немає.

```json
"groupId": {
    "type": "string",
    "nullable": true,
    "references": { "collection": "groups", "onDelete": "setNull" }
}
```

```json
"childIds": {
    "type": "array",
    "default": [],
    "items": { "references": { "collection": "kids", "onDelete": "remove" } }
}
```

### Правила `onDelete`

Що станеться з записами, які посилаються на запис, що видаляється:

| Правило                       | Для            | Дія                                                                         |
| ----------------------------- | -------------- | --------------------------------------------------------------------------- |
| `restrict` (за замовчуванням) | рядка й масиву | видалення заборонено: `409 REFERENCE_RESTRICT` з переліком, хто посилається |
| `setNull`                     | рядка          | посилання стає `null`; колонка має бути `nullable`                          |
| `remove`                      | масиву         | `id` прибирається з масиву                                                  |

Каскадного видалення немає свідомо. Правила на кшталт «видалити групу, з якої видалили останню дитину» — це бізнес-логіка, і вона живе в сервісах.

### Що перевіряється

- **`create`/`update`:** кожне посилання — `null` (якщо колонка `nullable`) або `id` існуючого запису потрібної колекції. Інакше `422 REFERENCE_NOT_FOUND`. Однакові `id` в одному масиві дають `422 VALIDATION_ERROR`.
- **`delete`:** правила застосовуються в тій самій транзакції, що й видалення. Звіт показує, які записи змінились:

    ```js
    const report = await db.delete('groups', groupId);
    // { deleted: [{ collection: 'groups', id: groupId }],
    //   updated: [{ collection: 'kids', id: kidId, fields: ['groupId'] }] }
    ```

- **Старт бази:** посилання, що вказують на неіснуючі записи (наприклад, після ручного видалення файлу), зупиняють запуск з `BROKEN_REFERENCES` і переліком таких посилань.

### Обмеження конфігу

- `references` — лише для `string`, `items.references` — лише для `array`.
- Значення за замовчуванням: `null` для посилання, `[]` для масиву.
- Інший бік зв'язку рушій не синхронізує: якщо в дитини є `parentIds`, а в батьків — `childIds`, це два незалежні поля. Краще зберігати зв'язок з одного боку.

## 7. Унікальні колонки (`unique`)

```json
"email": { "type": "string", "nullable": true, "unique": true }
```

- **Дозволено** для `string`, `number`, `integer` і `boolean`.
- **Значення, яке вже є в іншого запису,** дає `409 UNIQUE_VIOLATION` з текстом `"email" must be unique.` У повідомленні немає ні самого значення, ні `id` власника.
- **`null` і відсутнє поле** не конфліктують: багато записів можуть бути без значення.
- **Рядки порівнюються з урахуванням регістру.** Email варто нормалізувати (`toLowerCase()`) у сервісі.
- **Перевірка виконується при кожній операції,** тож обміняти значення двох записів одним кроком не можна. Обмін робиться в одній транзакції через `null`:

    ```js
    await db.transaction(async (tx) => {
        await tx.update('parents', a.id, { email: null });
        await tx.update('parents', b.id, { email: oldEmailOfA });
        await tx.update('parents', a.id, { email: oldEmailOfB });
    });
    ```

- **`unique` разом із `references`** дає зв'язок «один до одного». Наприклад, одне приміщення на групу:

    ```json
    "roomId": {
        "type": "string",
        "nullable": true,
        "unique": true,
        "references": { "collection": "rooms", "onDelete": "setNull" }
    }
    ```

- **Дублікати, що вже є в даних** (наприклад, `unique` додали до колонки з даними), при старті дають попередження `DUPLICATE_VALUE`, а не помилку. Такі записи можна редагувати: перевіряються лише значення, які змінюються. Віддати дубльоване значення ще одному запису не можна.

## 8. Транзакції

Транзакція — група змін, яка застосовується повністю або не застосовується зовсім.

```js
const result = await db.transaction(async (tx) => {
    // tx.get, tx.list, tx.create, tx.update, tx.delete — як у db
    return something; // стане результатом db.transaction
});
```

- **Звичайне завершення функції** — усі зміни записуються атомарно (коміт).
- **Виняток (`throw`)** — жодна зміна не записується, виняток летить назовні.
- **`tx.rollback(value)`** — жодна зміна не записується, `db.transaction` повертає `value`.

Усередині транзакції всі операції бачать її власні незакомічені зміни: щойно створений запис можна знайти через `tx.get`/`tx.list` і на нього можна послатися. Інші запити бачать лише закомічені дані.

### Приклади

**Кілька пов'язаних записів разом**

```js
const { group, kids } = await db.transaction(async (tx) => {
    const group = await tx.create('groups', {
        name: 'Сонечко',
        minAge: 3,
        maxAge: 3,
    });
    const kids = [];
    for (const kid of newKids) {
        kids.push(await tx.create('kids', { ...kid, groupId: group.id }));
    }
    return { group, kids };
});
// якщо хоч одна дитина не пройде перевірку — не буде ні групи, ні дітей
```

**Бізнес-правило з перевіркою і відмовою**

```js
await db.transaction(async (tx) => {
    const group = await tx.get('groups', groupId);
    const { total } = await tx.list('kids', { where: { groupId }, limit: 1 });
    if (total >= group.capacity) {
        throw new HttpError(
            StatusCodes.CONFLICT,
            'GROUP_IS_FULL',
            'The group is full.'
        );
    }
    await tx.update('kids', kidId, { groupId });
});
```

Між перевіркою кількості й записом ніхто інший не може додати дитину в ту саму групу: транзакції ізольовані.

**Видалення з наслідками (FR-018: видалити групу, якщо в ній не лишилось дітей)**

```js
await db.transaction(async (tx) => {
    const kid = await tx.get('kids', kidId);
    await tx.delete('kids', kidId);
    if (kid.groupId) {
        const { total } = await tx.list('kids', {
            where: { groupId: kid.groupId },
            limit: 1,
        });
        if (total === 0) await tx.delete('groups', kid.groupId);
    }
});
```

**Відкат зі значенням (наприклад, «пробний запуск»)**

```js
const preview = await db.transaction(async (tx) => {
    await tx.update('groups', groupId, { capacity: 15 });
    const { items } = await tx.list('kids', {
        where: { groupId },
        sort: 'lastName',
    });
    return tx.rollback(items); // показати результат, але нічого не зберігати
});
```

**Обробка помилки окремої операції всередині транзакції**

```js
await db.transaction(async (tx) => {
    for (const parent of imported) {
        try {
            await tx.create('parents', parent);
        } catch (error) {
            if (error.code !== 'UNIQUE_VIOLATION') throw error; // дублікати пропускаємо
        }
    }
});
```

Перехоплена помилка операції не відкочує транзакцію: відкочується лише сама невдала операція.

**Довша транзакція**

```js
await db.transaction(
    async (tx) => {
        /* генерація розкладу */
    },
    { timeout: 60_000 }
);
```

### Правила

- **Ізоляція повна:** у кожен момент виконується одна транзакція, що змінює дані. Інші транзакції та звичайні `create`/`update`/`delete` чекають своєї черги. Читання (`db.get`/`db.list`) виконуються паралельно й бачать лише закомічений стан.
- **Тайм-аут:** за замовчуванням `transactionTimeout` з конструктора (10 с), для окремої транзакції — `{ timeout }`, `0` вимикає ліміт. Транзакція, що не вклалася, відкочується з `503 TRANSACTION_TIMEOUT`. Ліміт діє на функцію-тіло; почавшись, коміт завжди доходить до кінця.
- **Усередині транзакції використовуйте лише `tx`.** Виклик `db.create` / `db.get` / … з тіла транзакції дає `INVALID_TRANSACTION_USE`. `db.collections()` і `db.schema()` дозволені.
- **Об'єкт `tx` живе, лише поки виконується транзакція.** Після завершення його операції дають `TRANSACTION_CLOSED`.
- **Операції однієї транзакції виконуються по черзі,** навіть якщо їх запустили через `Promise.all`. Операції, які забули `await`-нути, дочікуються перед комітом.
- **`tx.rollback()` спрацьовує,** навіть якщо його сигнал перехопить `try/catch` усередині тіла.

## 9. Надійність

- **Журнал транзакцій.** Кожен коміт спершу повністю записується в `database/journal.json`, і лише потім змінюються файли записів. Якщо процес упаде посередині, наступний старт застосує журнал повністю. Транзакція або є вся, або її немає.
- **Атомарні файли.** Кожен файл (запис, журнал) пишеться через тимчасовий файл і `rename` з `fsync`: обірваний запис не псує файл.
- **Збої диска під час коміту.** Якщо застосувати закомічені зміни не вдалося, база переходить у стан `503 DATABASE_NEEDS_RECOVERY` і не приймає запитів до перезапуску; при перезапуску журнал доводить коміт до кінця. Якщо не вдалося лише видалити журнал, читання працює далі, а запис блокується до перезапуску.
- **Прибирання.** Залишки тимчасових файлів після аварії видаляються при старті.

`database/journal.json` і `database/.lock` — службові файли, вони в `.gitignore`.

## 10. Життєвий цикл бази

### Старт: `init()`

1. Зайняти директорію бази (див. нижче).
2. Прочитати й перевірити всі `config.json`.
3. Побудувати граф зв'язків.
4. Завантажити `id` записів та індекси.
5. Застосувати журнал, якщо попередній процес упав посеред коміту.
6. Перевірити, що всі посилання ведуть до існуючих записів.
7. Знайти дублікати в `unique`-колонках.

Якщо будь-який крок не вдався, база лишається закритою, а `init()` кидає помилку. Сервер у такому разі не стартує.

**Попередження.** Проблеми, що не заважають роботі, не зупиняють старт. Вони потрапляють у `db.warnings` і в лог:

| Код               | Коли                                                |
| ----------------- | --------------------------------------------------- |
| `INVALID_RECORD`  | запис не відповідає поточній схемі (розділ 2)       |
| `DUPLICATE_VALUE` | значення в `unique`-колонці повторюється (розділ 7) |

```js
await db.init();
for (const warning of db.warnings) {
    // { code: 'INVALID_RECORD', collection: 'kids', id: '…', message: 'Unknown field "age".' }
}
```

### Одна директорія — один сервер

Директорію бази може використовувати лише один відкритий екземпляр `FileDatabase`. Другий сервер на тій самій директорії (або другий `new FileDatabase(...)` в тому самому процесі) не стартує з `503 DATABASE_LOCKED`. Після аварійного завершення наступний старт відбувається як звичайно.

### Зупинка: `close()`

- Нові виклики одразу отримують `503 DATABASE_CLOSED`.
- Поточна транзакція, операції в черзі та читання доходять до кінця.
- Потім директорія звільняється, і базу можна відкрити знову (`init()`).

Сервер (`src/server.js`) викликає `close()` при `SIGTERM` і `SIGINT` (Ctrl+C), після зупинки HTTP-сервера.

## 11. Логування

### Рушій

Рушій не обирає бібліотеку логування сам: логер передає застосунок.

```js
new FileDatabase(root, { logger });
```

Логер — будь-який об'єкт з методами `debug`, `info`, `warn` та `error`, що приймають `(поля, повідомлення)`. Сюди підходить `pino`, дочірній логер `pino` чи навіть `console`. Без логера `debug`/`info` мовчать, а `warn`/`error` пишуться в `console`.

| Рівень  | Що рушій пише                                                                                                                                                                |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `info`  | база відкрита (колекції, записи, попередження, час); база закрита                                                                                                            |
| `warn`  | попередження старту; застосовано журнал після аварії; директорію перехоплено після аварії іншого процесу; тайм-аут транзакції; невдалий запис журналу (транзакцію відкинуто) |
| `error` | не вдалося застосувати коміт; не вдалося видалити журнал                                                                                                                     |
| `debug` | кожен коміт (скільки змін, у яких колекціях, тривалість); відкат; невдала транзакція (код помилки)                                                                           |

**Рушій ніколи не пише в лог вміст записів** — лише колекції, `id`, кількість, тривалість і коди помилок. У базі особисті дані дітей і батьків, і в логах їм не місце.

### Застосунок

- `src/logger.js` — логер `pino`: JSON-рядки в stdout.
- Рівень задає змінна `LOG_LEVEL` (`debug`, `info`, `warn`, `error`; за замовчуванням `info`).
- `npm run dev` показує логи у читабельному вигляді (`pino-pretty`), `npm start` пише JSON для систем збору логів.
- Кожен HTTP-запит отримує `requestId`: із заголовка `x-request-id`, якщо він схожий на ідентифікатор, інакше генерується. Він повертається в заголовку відповіді й автоматично додається до **всіх** записів логу цього запиту, зокрема й записів рушія.
- Рядок доступу на кожен запит містить метод, шлях **без рядка запиту** (у `?where=` можуть бути імена), статус і тривалість. Заголовки `authorization` і `cookie` маскуються.

```json
{"level":20,"module":"storage","requestId":"5c2e…","changes":1,"collections":{"kids":1},"ms":3,"msg":"Transaction committed"}
{"level":30,"requestId":"5c2e…","req":{"method":"POST","path":"/api/kids"},"res":{"statusCode":201},"responseTime":12,"msg":"request completed"}
```

## 12. Помилки

Рушій кидає `DatabaseError` з полями:

- `code` — машинний код (таблиця нижче);
- `status` — HTTP-статус, з яким варто відповісти;
- `message` — опис для людини.

HTTP-обробник помилок (`src/app.js`) відповідає саме цим статусом. Вищі рівні (роути, сервіси) кидають `HttpError` зі статусом із пакета `http-status-codes`:

```js
import { StatusCodes } from 'http-status-codes';
import { HttpError } from '../http-error.js';

throw new HttpError(
    StatusCodes.CONFLICT,
    'GROUP_IS_FULL',
    'The group is full.'
);
```

Перевірити конкретну помилку рушія в сервісі:

```js
try {
    await db.create('parents', parent);
} catch (error) {
    if (error.status === StatusCodes.CONFLICT) {
        /* дублікат або заборонене видалення */
    }
    if (error.code === 'UNIQUE_VIOLATION') {
        /* саме дублікат */
    }
    throw error;
}
```

Кожен код прив'язаний до свого статусу в одному місці — каталозі `DatabaseErrors` у `src/storage/errors.js`.

| Статус | Код                            | Коли                                                                 |
| ------ | ------------------------------ | -------------------------------------------------------------------- |
| 400    | `INVALID_BODY`                 | тіло запису — не JSON-об'єкт                                         |
| 400    | `INVALID_ID`                   | `id` — не UUIDv7                                                     |
| 400    | `INVALID_QUERY`                | неправильний фільтр, сортування чи пагінація                         |
| 400    | `INVALID_COLLECTION`           | неправильне ім'я колекції                                            |
| 404    | `NOT_FOUND`                    | запису з таким `id` немає                                            |
| 404    | `COLLECTION_NOT_FOUND`         | колекції з таким ім'ям немає                                         |
| 409    | `REFERENCE_RESTRICT`           | запис не можна видалити: на нього посилаються (`onDelete: restrict`) |
| 409    | `UNIQUE_VIOLATION`             | значення `unique`-колонки вже є в іншого запису                      |
| 422    | `VALIDATION_ERROR`             | запис не відповідає схемі                                            |
| 422    | `REFERENCE_NOT_FOUND`          | посилання на неіснуючий запис                                        |
| 500    | `INVALID_CONFIG`               | помилка в `config.json`                                              |
| 500    | `CORRUPT_RECORD`               | файл запису не читається або має неправильний `id`                   |
| 500    | `CORRUPT_JOURNAL`              | журнал транзакцій пошкоджений                                        |
| 500    | `BROKEN_REFERENCES`            | збережені записи посилаються на неіснуючі                            |
| 500    | `INVALID_TRANSACTION_USE`      | у транзакції викликано `db` замість `tx`                             |
| 500    | `TRANSACTION_CLOSED`           | `tx` використано після завершення транзакції                         |
| 500    | `DATABASE_ALREADY_INITIALIZED` | `init()` на вже відкритій базі                                       |
| 503    | `DATABASE_NOT_READY`           | `init()` ще не завершився                                            |
| 503    | `DATABASE_CLOSED`              | база закрита або закривається                                        |
| 503    | `DATABASE_LOCKED`              | директорію бази використовує інший сервер                            |
| 503    | `DATABASE_NEEDS_RECOVERY`      | збій диска під час коміту; допоможе перезапуск                       |
| 503    | `TRANSACTION_TIMEOUT`          | транзакція не вклалася в ліміт часу й відкочена                      |

Загалом: `4xx` — проблема в запиті клієнта; `500` — помилка конфігурації, даних чи використання рушія в коді; `503` — тимчасовий стан бази.

## 13. Обмеження

Рушій розрахований на дані садка — сотні, до кількох тисяч записів. Свідомо не реалізовано:

- **JOIN-ів і підтягування пов'язаних записів.** Пов'язані записи читаються окремими запитами (`get` за `id` або `list` з `where`).
- **Каскадного видалення.** Наслідки видалення понад `setNull`/`remove` реалізуються в сервісах у транзакції (розділ 8).
- **Складеної унікальності** (унікальна пара полів) та унікальності без урахування регістру.
- **Паралельних записів.** Транзакції, що змінюють дані, виконуються по черзі. Читання паралельні.
- **Міграцій схеми.** Замість них — попередження при старті й поступове виправлення записів через `PATCH` (розділ 2).
- **Ліміту на очікування в черзі.** Обмежено лише тривалість самої транзакції.
- **Тримання записів у пам'яті.** Фільтр без індексу й сортування за полем читають записи-кандидати з диска.
