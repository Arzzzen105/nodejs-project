# 🏛️ Архітектура кастомного файлового рушія БД (Custom File-DB Engine)

Це технічний документ із описом архітектури локальної файлової бази даних, розробленої для системи управління дитячим садком на платформі **Node.js**.

Рішення побудоване суворо на нативних модулях **без використання зовнішніх СУБД та npm-пакетів**.

---

## 1. Концепція збереження даних (Storage Layout)

Замість монолітного JSON-файлу обрано підхід **«Таблиця = Директорія, Запис = JSON-файл»**.
```
database/ 
    ├── kids/
    │   ├── config.json
    │   │
    │   ├── 8f3a9a12-....json
    │   │
    │   └── c4b2e8f1-....json
    │
    ├── groups/
    │   ├── config.json
    │   │
    │   └── 3d1f2b45-....json
    │
    └── teachers/
        ├── config.json
        │
        └── e9a87b12-....json└── menu/└── 2026-10-09.json
```

### Основні рішення:
* **Первинний ключ (Primary Key):** Використовується **UUID v4**. Це знімає потребу в глобальних автоінкрементних лічильниках та блокуванні всієї бази при виконанні `INSERT`.
* **Доступ за ID:** Отримання запису за його UUID відбувається за $O(1)$ через пряме звернення до файлової системи ОС (`fs.readFile('./database/kids/{uuid}.json')`).
* **Config файл таблиці**: В кожній папці-таблиці повинен існувати `config.json`, який визначає її структуру, обмеження на колонки тощо. Подальша структура цього файлу ще в розробці.

## 2. Гарантія цілісності даних (Data Integrity)

### 2.1 Атомарність запису (Atomic Writes)
Щоб запобігти пошкодженню JSON-файлів при раптовому збої живлення чи падінні Node.js-процесу, операції створення та оновлення виконуються через тимчасовий файл:

1. Дані записуються у файл з розширенням `.tmp` (`path/id.json.tmp`).
2. Виконується нативна атомарна операція ОС — `fs.rename(tmpPath, targetPath)`.
3. Операція заміна файлу відбувається транзакційно на рівні файлової системи.

[Дані в RAM] ──> writeFile() ──> [file.json.tmp] ──> rename() ──> [file.json]
### 2.2 Ізоляція та захист від Race Condition (File Locks)
Для уникнення колізій під час паралельних операцій `UPDATE` над одним і тим самим файлом реалізовано межанізм **In-Memory Promise Locks** на рівні ID:

* На кожен ідентифікатор створюється ланцюжок `Promise` (Chaining).
* Паралельні запити на зміну одного запису стають у чергу й виконуються послідовно.
* Операції над *різними* файлами виконуються паралельно без блокувань.

## 3. Продуктивність та індексація (RAM Indexing)

Для уникнення повільного Full Scan (`fs.readdir` + читання кожного файлу) при виконанні запитів типу `SELECT WHERE field = value` використовуються **вторинні індекси в оперативній пам'яті**.

### Механіка роботи:
1. **Ініціалізація (Startup Scan):** При старті сервера рушій 1 раз сканує директорії й будує структури даних у RAM:
   ```javascript
   // Map<FieldName, Map<Value, Set<UUID>>>
   indexes = Map {
     'age' => Map { 3 => Set {'uuid-1', 'uuid-2'}, 4 => Set {'uuid-3'} },
     'groupId' => Map { 'group-1' => Set {'uuid-1'} }
   } 
   ```
**Мутації (Sync)**: При виконанні CREATE, UPDATE або DELETE рушій оновлює як файл на диску, так і RAM-індекс.

__На майбутнє__: Імовірне застосування бінарного дерева пошуку всередині таблиці-індексів замість простого масиву.

## 4. Планувальник запитів (Query Planner)
При виклику методу db.select(collection, { where }) рушій автоматично обирає найшвидшу стратегію:
```
                  ┌───────────────────────────┐
                  │ Запит: select(collection) │
                  └─────────────┬─────────────┘
                                │
                      / Перевірка WHERE /
                                │
         ┌──────────────────────┼──────────────────────┐
         ▼                      ▼                      ▼
  [ Є where.id? ]     [ Є RAM-індекс? ]      [ Немає індексу ]
         │                      │                      │
         ▼                      ▼                      ▼
  ★ PK Lookup O(1)     ★ Index Scan O(1)      ★ Full Scan O(N)
  Читаємо 1 файл       Вибираємо ID з RAM     Читаємо всі файли
  напряму з диска      та читаємо їх          з директорії
```

## 5. Моделювання зв'язків (Relationships & Joins)
Враховуючи документну природу збереження даних, обрано гібридну модель зв'язків:
### 5.1 Вкладення (Embedding / Single Source of Truth)
Дані, які належать суворо одній сутності (наприклад, медична картка або список алергій дитини), зберігаються прямо в JSON-файлі дитини без створення окремих таблиць:
```
JSON{
  "id": "kid-uuid-1",
  "name": "Арсен",
  "age": 3,
  "groupId": "group-uuid-10",
  "medicalInfo": {
    "bloodType": "A+",
    "allergies": ["горіхи"]
  }
}
```
### 5.2 Application-Level Join
Зв'язки між незалежними сутностями (Kids -> Groups -> Teachers) реалізуються на рівні рушія за допомогою однопрохідної вибірки через $in за $O(1)$: <br>
Зчитується документ дитини (з посиланням groupId). Робиться швидкий точковий виклик до колекції groups за ID. Об'єкти збираються в єдине дерево й повертаються клієнту.

## 6. Компонентна архітектура (Architecture Layering)Розділення відповідальності реалізовано через Composition over Inheritance: 
```
 ┌─────────────────────────────────────────────────────────┐
 │                    HTTP Controlers                      │
 └────────────────────────────┬────────────────────────────┘
                              │
 ┌────────────────────────────▼────────────────────────────┐
 │                  Domain Repositories                    │
 │    (KidsRepository, GroupsRepository, TeachersRepo)     │
 └────────────────────────────┬────────────────────────────┘
                              │  Виклики: select(), insert()
 ┌────────────────────────────▼────────────────────────────┐
 │                     FileDBEngine                        │
 │  (I/O, Atomic Rename, Promise Locks, Query Planner)     │
 └────────────────────────────┬────────────────────────────┘
                              │
 ┌────────────────────────────▼────────────────────────────┐
 │                OS File System (JSON Files)              │
 └─────────────────────────────────────────────────────────┘
```
* FileDBEngine (Нижній шар / Driver): Відповідає суто за файлові операції, локи, атомарність, підтримку RAM-індексів та вибірку сирих JSON-об'єктів.
* Repositories (Верхній шар / Domain): Не знають про файлову систему fs. Вони лише формують декларовані запити до FileDBEngine та маплять JSON у бізнес-моделі.

7. Переваги обраного рішення
* Безпека: Нуль сторонніх npm-залежностей (Zero Dependencies).
* Прозорість: Дані збережені у стандартному human-readable форматі JSON.
* Стійкість до сбоїв: Атомарні записи гасять ризик битих файлів при аварійному зупиненні процесу.
* Масштабованість під задачу: Завдяки RAM-індексам та точковим файловим вибіркам за $O(1)$, система працюватиме миттєво при обсягах даних дитячого садка (до десятків тисяч записів).
