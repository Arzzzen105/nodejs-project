# Вимоги до сервера

## 1. Мета продукту

### 1.1. Загальний опис

Кінцевий продукт - це серверна інформаційна система, що виконує функції збереження, управління та обробки даних про дитячий садок (діти, батьки, робітники тощо).

### 1.2 Мета продукту

- централізовано берігати дані про ключові сутності садка
- керувати основними сутностями садка
- автоматизовано генерувати розклад занять для дітей
- обчислювати загальний прибуток від садка
- опрацьовувати систему знижок та пільг
- вести облік платежів

### 1.3 Межі

Даний продукт не передбачає розробку клієнтної частини (frontend). Кінцевим результатим має бути лише серверна частина, що задовільняє вищезгаданим завданням.

## 2. Користувачі системи та їх ролі

### 2.1 Адміністратор (дід)

Дід - суперадмін, що має доступ до усіх даних та може модифікувати їх якзавгодно. Діда цікавлять гроші

Дід може:

- Виконувати CRUD-операції над усіма сутностями системи
- Реєструвати дітей
- Змінювати зарплати інших працівників
- Отримувати фінансові звіти
- Прогнозувати прибуток для гіпотетичної кількості дітей (симуляція)

Фактично дід може все.

### 2.2 Менеджер

Менеджер виконує адміністративні функції, але з обмеженим доступом.

Можливості менеджера:

- реєстрація дітей;
- додавання та редагування інформації про дітей і батьків;
- створення та редагування груп;
- призначення дітей до груп;
- перегляд інформації про працівників;
- робота з розкладом у межах наданих прав;
- виконання інших дозволених адміністративних операцій.

Менеджер не має повного доступу до управління фінансовими налаштуваннями та правами адміністратора.

### 2.3 Вихователь

Вихователь закріплюється за якоюсь одною конкретною групою

Вихователь може:

- читати інформацію про дітей своєї групи (розширено, з батьками і тд)
- перегляд розкладу групи

Вихователь має рівно одну групу, а одна група має рівно одного вихователя

### 2.4 Викладач

Викладач закріплюється за певним набором предметів, які він може викладати.

Можливості викладача:

- перегляд свого розкладу;
- перегля груп, у яких він проводить заняття;
- перегляд списку дітей окремих груп, у яких він проводить заняття;
- коригування свого розкладу.

### 2.5 Помічник виохвателя

Вихователь закріплюється за якоюсь одною конкретною групою

Помічник не взаємодіє із системою.

Вихователь має рівно одну групу, а одна група має рівно одного вихователя

### 2.6 Батьки

Батьки мають право переглядати інформацію лише про своїх дітей та суміжну інформацію

Батьки можуть:

- переглядати інформацію про своїх дітей;
- переглядати скорочену інформацію про групи своїх дітей (список з прізвища і ім'я);
- додавання приміток про сввоїх дітей;
- перегляд розкладу групи своїх дітей;
- перегляд вартості навчання, харчування;
- перегляд харчування;
- перегляд пільг своєї дитини;
- оплачувати заняття та харчування;

Батьки не можуть переглядати персональні про чужих дітей.

Батьки можуть мати декількох дітей в межах садіка.

## 3. Основні сутності системи

Система повинна передбачати зберігання інформації про такі сутності:

| Сутність          | Призначення                      |
| ----------------- | -------------------------------- |
| User              | Обліковий запис користувача      |
| Child             | Інформація про дитину            |
| Parent            | Інформація про батьків           |
| Relative          | Інформація про родичів дитини    |
| Group             | Група дітей одного віку          |
| Employee          | Інформація про працівника        |
| Educator          | Вихователь групи                 |
| Assistant         | Помічник вихователя              |
| Teacher           | Викладач дисципліни              |
| Subject           | Навчальна дисципліна             |
| Lesson            | Конкретне заняття                |
| Schedule          | Розклад занять                   |
| Room              | Приміщення садочка               |
| Discount          | Пільга на навчання               |
| Meal              | Вартість та параметри харчування |
| Payment           | Інформація про оплату            |
| FinancialSettings | Фінансові параметри              |
| ChangeHistory     | Історія змін даних               |

Додаткові сутності, рекомендовані для чіткого розмежування відповідальності:

| Сутність               | Призначення                                                       |
| ---------------------- | ----------------------------------------------------------------- |
| Role / Permission      | Ролі та дозволені дії                                             |
| ScheduleItem           | Окремий запис розкладу: час, група, дисципліна, викладач, кімната |
| Invoice                | Рахунок із зафіксованими сумами та тарифами на момент нарахування |
| Payment                | Фактична оплата, що може покривати один або декілька рахунків     |
| TuitionPlan / MealRate | Налаштовувані тарифи навчання та харчування з періодом чинності   |
| Expense                | Фактичні витрати для фінансових звітів                            |
| AuditLog               | Журнал змін основних записів                                      |

**User** містить дані для входу та ролі доступу; **Parent** і **Employee** — бізнес-дані про відповідних осіб. Працівник може мати обліковий запис, але обліковий запис не повинен замінювати картку працівника.

Перелік сутностей є логічною моделлю предметної області. Під час проєктування бази даних окремі сутності можуть бути об'єднані або реалізовані через зв'язки між таблицями.

## 4. Функціональні вимоги

### FR-001. Керування дітьми

Система повинна надавати можливість адміністратору та менеджеру виконувати CRUD-операції над дітьми:

- створення дитини;
- редагування інформації про дитину;
- отримувати інформацію про дитину;
- призначати дитину в групу
- змінювати групу дитини

Основні атрибути дитини:

- ім'я та прізвище;
- вік;
- батьки;
- група;
- примітки (харчові вподобання тощо);
- пільги;
- потреба в послугах логопеда.

Значення атрибутів повинні задовільняти обмеженням, заданих бізнес-правилами.

### FR-002. Керування батьками

Система пивонна надавати можливість адміністратору та менеджеру виконувати CRUD-операціями над батьками:

- створення запису про батька
- видалення батька
- редагування батька
- прив'язка батька до дитини
- отримання інформації про батька

Основні атрибути батька:

- ім'я та прізвище;
- місце роботи;
- номер телефону;
- email;

### FR-003. Керування групами

Система пивонна надавати можливість адміністратору та менеджеру виконувати CRUD-операціями над батьками:

- створення групи;
- перегляд інформації про групу;
- редагування групи;
- видалення групи;
- додавання дітей в групу;
- видалення дітей з групи;
- призначення вихователя;
- призначення помічника;
- прзначення приміщеня під групу;

Основні атрибути групи:

- назва;
- діти;
- приміщення;
- вихователь;
- помічник вихователя.

Вміст атрибутів повинен відповідати бізнес вимоагм

### FR-004. Керування працівниками (вихователі, викладачі, помічники)

Адміністратор та моживість повинен мати можливість:

- додавати працівників;
- переглядати інформацію;
- редагувати інформацію;
- видаляти працівників;
- призначати працівників до груп або дисциплін.

Крім того, адміністратор (але не менеджер) може:

- змінювати ЗП працівників (зокрема ЗП менеджера).

### FR-005. Керування навчальними дисциплінами

А
Адміністратор та менеджер повинен мати можливість:

- створювати навчальні дисципліни;
- редагувати навчальні дисципліни;
- видаляти навчальні дисципліни;
- переглядати навчальні дисципліни;

Передбачено такі дисципліни:

1. Вільна боротьба
2. Фізична культура
3. Музика
4. Англійська мова
5. Шахи
6. Логопед

### FR-006. Формуванян розкладу

Система повинна за потреби генерувати чорнвий вигляд розклад.

Під час створення вона повинна враховувати:

- вік дітей;
- групи
- викладачів;
- дисципліни;
- приміщення, доступні для проведення занять
- час харчування;
- вільний час;
- час сну;
- тривалість робочого дня

Розклад повинен відповідати бізнес правилам

Чорновий розклад може бути відредагований адміністратором, менеджером або викладачем відповідно до своїх прав.

Розклад має два стани: **чорновий** та **опублікований**. Для переходу з **чорнового** стану в **опублікований** система має перевірити його на відсутність конфлфіктів

Розклад повинен зберігати групу, приміщення, викладача, дисципліну, початок занять та кінець занять. Навантаження та тривалість занять можуть бути змінені адміністратором або менеджером.

При редагуванні розкладу нові зміни не повинні породжувати конфлікти.

### FR-007. Рівномірність розкладу

Згенерований/оновлений розклад повинен бути **рівномірним**.

**Рівномірний розклад** - це розклад, при якому для всіх груп однакового віку той самий предмет зустрічаєтсья однакову кількість раз за тиждень.

### FR-008. Режим дня

Під час робочого дня, що триває 8 годин, для дітей передбачено:

- сонний час (1 година);
- триразове харчування (3 по 30 хв);
- навчальні заняття;
- вільний час;

Вільний час - час, коли група не перебуває на заняття, не спить і не їсть.

### FR-009. Керування приміщеннями

Адміністратор та менеджер може:

- переглядати список приміщень;
- змінювати призначення приміщення;
- закріплювати приміщення за групою
- визначати навчальний предмет, який викладатиметься в приміщенні
- перевіряти доступність приміщення.

Кімнати мають два призначення:

1. Для групи
2. Для занять

Деякі приміщення можуть бути такими, в якими проводяться два предмети (наразі таким є лише спортзал: в ньому проводиться фізра та вільна боротьба).

В одному приміщенні може бути лише одна група. В кожної групи є своє приміщення.

### FR-010. Керування харчуванням

Система зберігає інформацію про вартість харчування. Вартість залежить від віку:

| Вік     | Вартість за день |
| ------- | ---------------: |
| 2 роки  |          300 грн |
| 3 роки  |          400 грн |
| 4 роки  |          500 грн |
| 5 років |          600 грн |

Адміністратор може змінювати вартість харчування.

### FR-011. Керування пільгами

Адміністратор може:

- переглядати інформацію про пільги;
- призначати дитині пільги;
- видаляти пільги;
- змінювати пільгу;

Пільги застосовуються лише до вратості навчання. Харчування не враховуєтсья в пільги.

### FR-012. Розрахунок вартості навчання

Система повинна вміти розраховувати кінцеву вартість користуванян послугами садка. Для цього вона враховує:

1. Базову вартість навчання (15000 грн)
2. Пільгу
3. Суму після врахування пільги
4. Вартість харчування
5. Кінцеву суму

### FR-013. Оплата на рік

Система повинна враховувати можливість оплачувати навчання дитини на рік наперед. В цьому випадку на вартість навчання накладаєтсья знижка -12%. Ця знижка не впливає на вартість харчування.

### FR-014. Оплата та рахунки

Система повинна відокремлювати **Invoice** (нарахування) від **Payment** (фактично отримані кошти). Рахунок містить окремі рядки навчання, індивідуальної знижки, річної знижки та харчування, а також підсумкову суму й період.

Система повинна підтримувати:

- створення запису про оплату;
- перегляд платежів;
- прив'язку платежу до дитини;
- визначення періоду оплати;
- зберігання суми;
- зберігання дати платежу;
- перегляд історії платежів.

### FR-15. Історія змін

Система повинна передбачати збереження історії змін основних даних.

Історія повинна містити:

- ідентифікатор зміненої сутності;
- тип операції;
- дату та час;
- користувача;
- попереднє значення;
- нове значення.

### FR-016. Керування фінансовими даними

Адміністратор може керувати:

- вартістю навчання;
- значущістю пільг;
- вартістю харчування;
- знижкою при річній оплаті;
- заробітні плати;
- вартість приміщень;

### FR-017. Розрахунок прибутку

Система повинна надавати адміністратору можливість отримати:

- дохід окремої групи;
- витрати окремої групи;
- прибуток окремої групи;
- загальний дохід садочка;
- загальні витрати садочка;
- загальний прибуток.

Розрахунок повинен враховувати оплату навчання, харчування, пільги, зарплати працівників та встановлені витрати.

Вартість харчування, сплачена батьками, повинна враховуватися як дохід, а вартість замовлення харчування — як витрата. Необхідно уникати подвійного врахування цих сум. Звіт має явно вказувати розрахунковий період та метод обліку доходу: нарахування за послуги або отримані платежі. Передоплата за рік не повинна механічно збільшувати прибуток одного місяця за всі 12 місяців у звіті за нарахуваннями.

### FR-018. Вимоги щодо видалення сутностей

Система повинна забезпечувати особливості операції видалення деяких сутностей:

1. Видалення групи:
    - діти, що належали цій групі, стає безгрупними;
    - вихователь та помічник залишаються залишаються в системі, але втрачають прив'язку до групи;
2. Видалення дітей:
    - якщо з групи була видалена остання дитина, то ця група має бути видалена з бази даних (визователь та помічник лишаютсья в базі);
    - якщо батьки, дитину яких видалили, більше не мають дітей в цьому садку, то ці батьки видаляються разом з дитиною;
3. Видалення вихователя/помічника:
    - група залишаються в базі, але втрачає вихователя;

### FR-019. Перевірка цілісності зв'язків

Система повинна надавати адміну та менеджеру можливість:

- виявляти дітей, які не належать ні одній групі;
- виявляти групи, яким не призначено вихователя або помічника
- виявляти вихователів або помічників, яким не призначено групу
- виявляти групи, яким не призначено кімнату

### FR-020. Batch-додаванян дітей в групу

Система повинна надавати можливість додавати декількох дітей в групу за допомогою спеціального ендпойнту

### FR-021. Послуги логопеда в садку

Система повинна врахувати особливості занять в логопеда:

- логопед потребує окремого приміщення;
- якщо в групі є хоча б **одна** дитина, яка потребує послуги логопеда, ця група є такою, що відвідує заняття у логопеда
- при оновленні/генеруванні розкладу лише групи, які відвідують заняття логопеда, отримують заняття в нього

### FR-022. Реєстрація користувачів

Менеджер та дід повинні могти:

- реєструвати інших корисутвачів (викладач, батьки, вихователі);
- при реєстрації задавати їхні креденшли

Менеджер не може реєструвати менеджера.

## 5. Бізнес-правила

### 5.1 Діти та групи:

**BR-01.** До садочка приймаються діти віком від 2 до 5 років.

**BR-02.** Діти різного віку не можуть перебувати в одній групі.

**BR-03.** Максимальна кількість дітей у групі — 20.

**BR-04.** Кожна група повинна мати одного вихователя.

**BR-05.** Кожна група повинна мати одного помічника вихователя.

**BR-06.** Кожна група повинна мати окреме основне приміщення.

**BR-07.** Одна сім'я може мати декількох дітей у садочку.

**BR-08.** При модифікації віку дитини її група не обчислюється наново, вона залишаєтсья в своїй групі.

### 5.2. Приміщення

**BR-08.** Загальна кількість кімнат — 20.

**BR-09.** Кімната може бути призначена для групи або проведення занять.

**BR-10.** Кількість використовуваних кімнат не може перевищувати кількість доступних.

**BR-11.** Кожна група повинна мати окрему кімнату.

**BR-11.** Окремі приміщення (спортзал) може бути призначені для проведення декількох дисциплін за раз.

**BR-12.** Оскільки принаймні 5 приміщені зарезервовані під навчальні дисципліни (фізична культура та боротьба в одному приміщенні), то садок може прийняти не більше 15 груп.

### 5.3. Вартість послуг садка

**BR-13.** Базова вартість навчання — 15 000 грн на місяць.

**BR-14.** Харчування оплачується окремо.

**BR-15.** Вартість харчування для дворічної дитини — 300 грн на день.

**BR-16.** Для кожного наступного року віку вартість харчування збільшується на 100 грн за день.

**BR-17.** Адміністратор може змінювати вартість харчування.

### 5.4. Пільги та оплата

**BR-18.** Доступні рівні пільг — 10%, 20%, 30%.

**BR-19.** Пільги призначає адміністратор.

**BR-20.** Оплата за навчання може здійснюватися щомісячно або за рік наперед.

**BR-21.** Річна оплата передбачає знижку 12%.

**BR-22.** Спеціальна знижка за наявність декількох дітей в одній сім'ї не передбачена.

**BR-23.** Пільги застосовуються лише до навчання.

**BR-24.** Знижка річної оплати застосовується лише до навчання. Вона не впливає на харчування.

**BR-25.** Харчування можна оплачувати лише помісячно.

**BR-26.** Дохід від оплати батьками харчування є окремим від розходу на харчування, навіть якщо ці значення рівні. У звітах вони повинні появлятись окремими записами.

### 5.5. Працівники

**BR-27.** Заробітна плата менеджера — 80 000 грн на місяць.

**BR-28.** Заробітна плата викладача дисципліни — 40 000 грн на місяць.

**BR-29.** Базова зарплата помічника вихователя — 20 000 грн на місяць.

**BR-30.** Зарплата вихователя розраховується за ставкою 2 000 грн за кожну дитину в групі.

**BR-31.** За кожну дитину понад 12 вихователь додатково отримує 5 000 грн.

**BR-32.** За кожну дитину понад 12 помічник додатково отримує 3 000 грн.

**BR-33.** Адміністратор може змінювати заробітні плати та ставки доплат.

### 5.6. Розклад

**BR-34.** Діти перебувають у садочку 8 годин на день.

**BR-35.** Сон триває 60 хвилин.

**BR-36.** Протягом дня передбачено три прийоми їжі по 30 хвилин.

**BR-37.** Прийоми їжі не можуть проходити підряд.

**BR-38.** Один викладач не може одночасно працювати з двома групами.

**BR-39.** Одна група не може одночасно відвідувати два заняття.

**BR-40.** Діти одного віку повинні отримувати однакову кількість занять.

**BR-41.** Вільний час може заповнювати проміжки між заняттями.

**BR-42.** Розклад є сталим на тиждень. У садку не передбачено парни/непарних тижнів.

**BR-43.** Садок працює 22 дня на місяць.

**BR-44.** Дитина гарантовано їсть тричі за день. Вона не може пропускати прийом їжі.

**BR-45.** При зміні стану системи розклад не оновлюється автоматично. Оновлення розкладу завжди тригериться лише руками.

**BR-46.** Для всіх груп однакового віку заняття з кожної дисципліни має зустрічатись однакову кількість разів за тиждень.

**BR-47.** Старші групи **не обов'язково** мають більшу кількість занять на тиждень, ніж молодші.

**BR-48.** Розклад може бути нерівномірним для викладачів (викладач може мати 10 занять одного дня, а наступного 0).

**BR-49.** Не вимагається однакова навантаженість для різних предметів.

**BR-50.** На дисципліни не накладаються вікові обмеження.

**BR-51.** Одне заняття триває 30 хв.

**BR-52.** Початкове навантаження кожного предмета - 2 заняття/тиждень. Це може змінюватись в залежності від фінансової вигоди.

**BR-53.** Заняття з будь-якої дисципліни не повинно проводитись двічі підряд.

**BR-54.** Наразі для дітей не передбачено перерв між заняттями, але в подальшому це може змінитись.

### 5.7. Автентифікація та авторизація

**BR-55.** Дід може реєструвати всіх користувачів.

**BR-56.** Менеджер може реєструвати може реєструвати всіх користувачів окрім менеджера.

**BR-57.** При реєстрації виконавець сам вказує дані для входу використувача (логін та пароль)

**BR-58.** ПКористувачі **не можуть** змінювати свої дані для входу після реєстрації (логін та пароль)

## 7. Нефункціональні вимоги

### NFR-01. Серверна архітектура

Система повинна працювати як серверний застосунок та надавати API.

### NFR-02. Зберігання даних

Інформація повинна зберігатися в базі даних і бути доступною після перезапуску сервера.

### NFR-03. Безпека

Система повинна забезпечувати автентифікацію та авторизацію користувачів.

### NFR-04. Конфіденційність

Користувачі не повинні отримувати доступ до персональних або фінансових даних без відповідних прав.

### NFR-05. Цілісність даних

Система повинна запобігати порушенню бізнес-правил, зокрема перевищенню місткості груп, конфліктам розкладу та неправильному призначенню кімнат.

### NFR-06. Конфігурованість

Фінансові параметри повинні зберігатися таким чином, щоб адміністратор міг змінювати їх без модифікації програмного коду.

### NFR-07. Розширюваність

Архітектура повинна дозволяти додавати нові дисципліни, фінансові правила та функції звітності.

### NFR-08. Документація API

API повинен мати опис доступних операцій, параметрів запитів, відповідей та помилок.

### NFR-09. RESTful API

Розроблена апі повинне відповідати принципам дизайну REST API.

### NFR-10. Перевірка даних і помилки API

API повинен повертати зрозумілі помилки валідації та відмови в доступі; недійсні операції (21-ша дитина, накладання занять, недозволений перегляд даних) не повинні змінювати базу даних.

### NFR-11. Стабільність фінансових операцій

Створення рахунка, реєстрація платежу та пов'язані зміни мають виконуватися узгоджено; повторний однаковий запит не повинен створювати подвійний платіж за наявності ідентифікатора операції.
