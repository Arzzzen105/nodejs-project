# Сервіси

Сервіс містить сценарії використання однієї сутності й бізнес-правила з [requirements.md](business/requirements.md). Він стоїть між контролером і репозиторіями: контролер розбирає HTTP-запит і викликає сервіс, а сервіс працює з даними лише через репозиторії ([repositories.md](repositories.md)).

Як влаштований HTTP-шар над сервісом, описано в [controllers.md](controllers.md).

Зразок — [KidService](../src/services/kid-service.js) і його тести, [kid-service.test.js](../tests/services/kid-service.test.js). Коли пишете свій сервіс, звіряйтеся з ними.

## 1. Як додати сервіс

1. Створити клас у `src/services/<сутність>-service.js`. Залежності приходять **одним об'єктом** і зберігаються в приватних полях:

    ```js
    export class GroupService {
        #uow;
        #groups;
        #kids;

        constructor({ uow, groups, kids }) {
            this.#uow = uow;
            this.#groups = groups;
            this.#kids = kids;
        }
    }
    ```

    З об'єктом нову залежність можна додати, не змінюючи сигнатури й усіх викликів.

2. Зареєструвати сервіс у [container.js](../src/container.js) під назвою колекції: `groups: new GroupService({ uow, groups: repositories.groups, kids: repositories.kids })`. Тест [container.test.js](../tests/app/container.test.js) впаде, якщо в репозиторію немає сервісу з тією самою назвою.

3. Мати щонайменше ці методи, з цими назвами: `list(query)`, `get(id)`, `create(data)`, `update(id, changes)`, `replace(id, data)`, `delete(id)`. Контролери покладатимуться на однакові назви в усіх сервісах. Методи без бізнес-правил просто передають виклик у репозиторій.

Базового класу для сервісів немає навмисно. З успадкованим `update` легко забути перевизначити метод, і він обійде бізнес-правило. Коли методи явні, сервіс уміє рівно те, що в ньому написано.

## 2. Домовленості

### Перевірка й запис — в одній транзакції

Якщо метод робить більше однієї операції, наприклад перевіряє місткість групи, а потім створює дитину, тіло загортається в `this.#uow.run(...)`:

```js
async create(data) {
    return this.#uow.run(async () => {
        await this.#assertRules({}, data);
        return this.#kids.create(data);
    });
}
```

Транзакції в базі виконуються по одній, тож між перевіркою й записом ніхто не змінить даних. Без `run` два одночасні запити обидва побачать 19 дітей, і в групі стане 21 (NFR-10).

### Бізнес-помилка — це `HttpError` зі своїм кодом

```js
throw new HttpError(
    StatusCodes.CONFLICT,
    'GROUP_FULL',
    'The group already has 20 kids.'
);
```

- **422 `UNPROCESSABLE_ENTITY`** — самі дані порушують правило (`MOTHER_NOT_FEMALE`, `GROUP_AGE_MISMATCH`).
- **409 `CONFLICT`** — дані правильні, але суперечать поточному стану бази (`GROUP_FULL`).
- Код пишеться в `UPPER_SNAKE_CASE` і наводиться в `@throws` методу. За кодом клієнт розрізняє помилки, тож один раз обраний код не змінюють.
- Ніколи не кидайте `new Error(...)`. Без `status` обробник помилок відповість `500`, ніби зламався сервер.

### Перевіряти лише те, що змінює запис

`update` (PATCH) отримує тільки змінені поля. Тому перевіряється запис **після** зміни, і лише та частина, яку зміна зачіпає:

```js
const current = await this.#kids.getById(id);
await this.#assertRules(current, { ...current, ...changes });
```

```js
// стать матері перевіряється, лише коли змінюється мати
if (next.motherId && next.motherId !== current.motherId) {
    /* ... */
}
```

Так запис, який став «неправильним» через зміну деінде (батькові змінили стать, дитина подорослішала за BR-08), лишається доступним для редагування. Для `create` поточний запис — `{}`, тож перевіряється все.

### Неіснуючі посилання перевіряє база

Якщо `groupId` вказує на запис, якого немає, сервіс пропускає свою перевірку. База сама відповість `422 REFERENCE_NOT_FOUND`. Пов'язаний запис беріть через `findById` (він повертає `null`), а не через `getById`: інакше клієнт отримає `404`, ніби не знайдено саму дитину.

Неправильний id (не UUIDv7) `findById` не прощає, він кидає `400 INVALID_ID`. Щоб відповідь була такою самою, як без сервісу, ловіть саме цей код (див. `#findReferenced` у `KidService`). Помилку окремої операції перехоплювати всередині `run` безпечно: на відміну від вкладеного `run`, вона не прирікає транзакцію ([repositories.md](repositories.md), розділ 6).

### Каскадів у базі немає, їх робить сервіс

`onDelete` у схемі вміє лише обнулити посилання (`setNull`), прибрати id з масиву (`remove`) або заборонити видалення (`restrict`, за замовчуванням). Якщо вимоги кажуть видаляти залежні записи разом із записом, сервіс видаляє їх сам, у тій самій транзакції. Приклад — `KidService.delete`: нотатки дитини (інакше `restrict` не дасть її видалити), потім дитина, потім батьки й група без дітей (FR-018).

Рахуйте залежні записи **після** видалення: транзакція вже бачить власні зміни, тож умова проста — «0 записів». Порожні посилання (`null`) пропускайте до підрахунку.

### Сервіс не знає про HTTP

Він не отримує `request` і `response` і не розбирає query string. На вхід приходять дані, на вихід — записи або `HttpError`. Тоді один сервіс можна викликати з контролера, з іншого сервісу чи з тесту.

### Інші сутності — через їхні репозиторії

Сервіс може отримати репозиторії інших сутностей: `KidService` читає `parents` і `groups`. Предикати й `where` лишаються в репозиторіях, сервіс викликає названі методи (`countByGroup`), див. [repositories.md](repositories.md), розділ 4.

### Посилання на вимоги

Біля правила в JSDoc і в назві тесту вказуйте його номер (`BR-08`, `FR-018`). Тоді видно, звідки правило взялося, і його легко знайти, коли вимога зміниться.

## 3. Тести

- Файл `tests/services/<сутність>-service.test.js`. Тести працюють над тимчасовою базою зі справжньою схемою з `database/`, а сервіс береться з `createContainer(db)` (див. `beforeEach` у [kid-service.test.js](../tests/services/kid-service.test.js)).
- На кожне правило потрібні три перевірки: правильні дані проходять; неправильні відхиляються з потрібними `status` і `code`; після відмови в базі нічого не змінилося.
- Дані, що обходять правила (наприклад, повна група), створюйте через репозиторій, а не через сервіс.
- Перевірте самі тести: тимчасово зламайте правило в сервісі, і хоча б один тест має впасти. Якщо не впав, правило не покрите.
