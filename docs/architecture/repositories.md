# Репозиторії й транзакції

Між сервісами й базою стоїть шар репозиторіїв: по одному на колекцію ([src/repositories/](../../src/repositories/)). Сервіси не звертаються до `FileDatabase` напряму. Вони отримують репозиторії, а коли кілька операцій мають виконатися разом, загортають їх в `uow.run(...)`.

Як писати самі сервіси, описано в [services.md](services.md).

## 1. Як усе зібрано

Усе створюється в одному місці, [src/container.js](../../src/container.js). Це аналог DI-контейнера, тільки явний:

```js
const uow = new UnitOfWork(database); // один на застосунок
const repositories = {
    kids: new KidRepository(uow),
    parents: new ParentRepository(uow),
    // ...
};
// сервіси отримують усе через конструктор:
// new KidService({ uow, kids: repositories.kids, parents: repositories.parents })
```

Класи нічого не створюють самі, а отримують залежності через конструктор. У застосунку контейнер доступний як `app.locals.container`. У тестах його можна зібрати над тимчасовою базою: `createContainer(testDb)`.

## 2. Як додати репозиторій

1. Створити клас-нащадок `BaseRepository` з назвою колекції:

    ```js
    import { BaseRepository } from './base-repository.js';

    export class KidRepository extends BaseRepository {
        constructor(uow) {
            super(uow, 'kids');
        }
    }
    ```

2. Зареєструвати його в `createContainer` під назвою колекції: `kids: new KidRepository(uow)`.

Якщо додати колекцію в `database/` і забути про репозиторій чи про реєстрацію, впаде тест [container.test.js](../../tests/app/container.test.js).

## 3. Що вміє кожен репозиторій

Методи [BaseRepository](../../src/repositories/base-repository.js):

| Метод                 | Повертає                                    | Якщо запису немає |
| --------------------- | ------------------------------------------- | ----------------- |
| `findById(id)`        | запис або `null`                            | `null`            |
| `getById(id)`         | запис                                       | `404 NOT_FOUND`   |
| `findPage(query)`     | `{ items, total, limit, offset }`           | порожня сторінка  |
| `create(data)`        | створений запис з `id`                      | —                 |
| `update(id, changes)` | запис після зміни (`PATCH`)                 | `404 NOT_FOUND`   |
| `replace(id, data)`   | запис після заміни (`PUT`)                  | `404 NOT_FOUND`   |
| `delete(id)`          | звіт: що видалено й кому обнулено посилання | `404 NOT_FOUND`   |

Для нащадків є ще:

- `this.db` — на чому викликати `get`/`list`/`create`/`update`/`delete`;
- `this.uow` — щоб загорнути метод з кількома операціями в `this.uow.run(...)`;
- `this.findAll(filter)` — усі записи за фільтром (розділ 5).

## 4. Домовленості

- **`find*` може нічого не знайти, `get*` — ні.** `find*` повертає `null` (один запис) або `[]` (список). `get*` повертає запис або кидає `404`. Беріть `findById`, коли від відсутності запису залежить, що робити далі, і `getById`, коли відсутність — помилка запиту. Неправильний `id` (не UUIDv7) — це `400 INVALID_ID` в обох випадках, а не «не знайдено».
- **Записи повертаються як зберігаються.** Зв'язки — це `id` (`groupId`, `motherId`), без вкладених об'єктів. Пов'язані записи завантажуються окремими методами, і лише тоді, коли сценарію вони потрібні (розділ 5). Повернутий запис — копія: змінювати його можна, у базі від цього нічого не зміниться.
- **Помилки бази проходять крізь репозиторій без змін.** `404`, `409 UNIQUE_VIOLATION`, `409 REFERENCE_RESTRICT`, `422 VALIDATION_ERROR` уже мають правильні статуси й доходять до клієнта як є.
- **Методи завжди `async`**, навіть однорядкові. У приреченій транзакції (розділ 6) `this.db` кидає помилку синхронно, і лише `async` перетворює її на відхилений Promise. Без нього `repo.findById(id).catch(...)` чи `Promise.all([...])` помилки б не побачили.
- **Предикати не виходять за межі репозиторію.** Сервіси викликають названі методи (`findByGroup`), а не складають `where`/`predicate` самі. Виняток — `findPage`: він для ендпоінтів, де фільтр приходить від клієнта в `?where=`.

## 5. Названі запити

Запити, потрібні бізнес-логіці, — це методи нащадка з назвою, що пояснює, навіщо вони:

```js
export class KidRepository extends BaseRepository {
    constructor(uow) {
        super(uow, 'kids');
    }

    async findByGroup(groupId) {
        return this.findAll({ where: { groupId } });
    }

    // зворотний бік зв'язку: діти, у яких цей батько — мати або батько
    async findByParent(parentId) {
        return this.findAll({
            predicate: or(eq('motherId', parentId), eq('fatherId', parentId)),
        });
    }

    // «неповні» діти: без матері чи батька
    async findIncomplete() {
        return this.findAll({
            predicate: or(eq('motherId', null), eq('fatherId', null)),
        });
    }
}
```

- **`findAll(filter)`** приймає `where`, `predicate` і `sort` і повертає **всі** записи. Ліміт `list` у 500 записів він обходить сам, читаючи сторінку за сторінкою в одній транзакції.
- **Пов'язані записи завантажуйте одним запитом на колекцію, а не в циклі:**

    ```js
    // батьки кількох дітей
    const ids = kids
        .flatMap((kid) => [kid.motherId, kid.fatherId])
        .filter(Boolean);
    const parents = await this.findAll({ predicate: inList('id', ids) });
    ```

    `inList` на `id`, як і посилання (`groupId`, `motherId`), працює через індекс.

- **Метод з кількома запитами, які мають бачити один стан бази,** загортається в `this.uow.run(...)`:

    ```js
    // у GroupRepository
    async findWithKids(id) {
        return this.uow.run(async () => {
            const group = await this.findById(id);
            if (!group) return null;
            const { items: kids } = await this.db.list('kids', { where: { groupId: id } });
            return { ...group, kids };
        });
    }
    ```

    Такий метод має сенс у репозиторії, якщо він потрібен кільком сервісам. Якщо лише одному, дані можна зібрати й у сервісі.

## 6. Транзакції

`uow.run(body)` виконує `body` у транзакції. Якщо `run` уже виконується вище за стеком викликів, новий **приєднується** до нього, а комміт робить той `run`, що відкрив транзакцію. Тож і сервіс, і репозиторій можуть загортати свою роботу в `run`, не знаючи, хто його відкрив:

```js
// KidService: видалення дитини за FR-018 (спрощено; повна версія — у src/services/kid-service.js)
async deleteKid(kidId) {
    return this.#uow.run(async () => {                      // відкриває транзакцію
        const kid = await this.#kids.getById(kidId);
        await this.#notes.deleteByKid(kidId);               // приєднується
        await this.#kids.delete(kidId);                      // motherId/fatherId зникають разом з дитиною

        // батьки без інших дітей видаляються
        for (const parentId of [kid.motherId, kid.fatherId].filter(Boolean)) {
            const kids = await this.#kids.findByParent(parentId);   // приєднується, бачить видалення вище
            if (kids.length === 0) await this.#parents.delete(parentId);
        }
        // ... група без дітей — так само
        return kid;
    });
}
```

Сервіс, що викликає інший сервіс, працює так само.

**Коли потрібен `run`:** щойно метод робить більше однієї операції. Для записів — щоб вони відбулися разом або не відбулися взагалі. Для читань — щоб між ними не пройшов чужий комміт. Одна операція атомарна й без нього. Параметри (`{ timeout }`) діють лише в `run`, що відкриває транзакцію, а у вкладеному ігноруються.

### Правила

1. **Будь-який `throw` у транзакції відкочує її всю, і назовні виходить перша помилка.** Вона доходить до `run`, який відкрив транзакцію, і той кидає її далі як є. Тож `HttpError` із сервісу, наприклад `409 GROUP_IS_FULL` з вкладеного сервісу, дійде до обробника помилок і до клієнта без змін. Вкладених транзакцій немає: є одна бізнес-операція, і виняток скасовує її цілком. До комміту зміни існують лише в пам'яті, тож відкат означає просто «не записувати».
2. **Перехопити помилку вкладеного `run` і продовжити не вийде.** Зміни, які він встиг зробити до помилки, вже в транзакції, тож вона приречена. Після такої помилки будь-яке звернення до бази в цій транзакції (`this.db`, вкладений `run`) одразу кидає ту саму першу помилку. А якщо зовнішній код усе ж завершиться успішно, `run` однаково відкотить транзакцію й кине її. Якщо дальші дії залежать від умови, перевірте її **перед** викликом:

    ```js
    // погано: виняток як розгалуження
    try {
        await groups.deleteIfEmpty(id);
    } catch {
        /* ... */
    }

    // добре
    if ((await kids.findByGroup(id)).length === 0) await groups.delete(id);
    ```

    Окрема операція — не `run`, і її помилку перехопити можна: невдала операція нічого не змінює. Тому й `findById` безпечно використовувати для розгалуження всередині транзакції.

3. **Не звертайтеся до бази повз репозиторії.** Якщо всередині `run` викликати `container.database` напряму, рушій відповість `INVALID_TRANSACTION_USE`. Це захист від взаємоблокування.
4. **Транзакція блокує записи інших, поки триває.** Записувач у базі один, тож у `run` не варто робити нічого повільного, наприклад звертатися до зовнішніх сервісів. Читання поза транзакцією не блокуються.
